# 确定性的文件锁边界探针

Status: implemented
Translation: current

[English](2026-10-15-file-lock-boundary-harness.md)

## 摘要

会话启动错误可能混淆排队、清理失败和死锁。本探针使用固定版本的 Effect、
内存文件系统和虚拟时钟，执行当前完整文件锁源码。它分别展示进程内排队不计入
获取锁的超时，以及原始删除仍在执行时，等待清理的调用可返回 `LockReleaseFailed`。
对照会将两种场景完全排空。这些结果说明已有边界，不证明新死锁或线上故障原因。

## 运行与来源

```sh
cd scripts/diagnostics/file-lock
npm ci --ignore-scripts --workspaces=false
npm run probe --silent
```

安装阶段仅准备锁定的 Effect 4.0.2，可能需要网络。实验本身离线，不使用真实
睡眠或性能阈值。使用仓库支持且提供 `stripTypeScriptTypes` 和
`--experimental-vm-modules` 的 Node。无需安装整个工作区。
合成结果记录于 `results.json`。

源码基线是 `a06a69f3e96eec68751ebd4df1d050cbbc4f1cea`，输出包含
`packages/shared/src/node/file-lock.ts` 的 SHA-256。探针只擦除类型，并以显式
能力链接完整模块，不重写队列或算法。VM 不是安全边界，只能运行可信源码。
默认文件系统层和进程门面已被替换，不访问真实锁、PID 或安装数据。

## 假设与独立执行

父代理设计实验，独立 `alchemist` 执行。历史与文件锁实验按顺序运行。

1. 持有者占用同名锁，第二个调用指定 120 秒获取超时。虚拟时间前进 600 秒后，
   它仍在队列中；不同名称的锁可继续执行。释放持有者后队列按顺序排空，文件
   全部清理。若排队期间触发超时，范围假设被证伪；若无法排空，对照无效。
2. 锁内工作成功，但合成删除操作由 Deferred 阻塞。超过五秒清理期限后，调用
   返回 `LockReleaseFailed`，原始删除仍拥有文件。放行原始删除后，同名锁可以
   再次获取，文件全部清理。立即删除作为阴性对照成功。若未失败、所有权丢失
   或无法恢复，则生命周期假设被证伪。

所有预测和对照均通过。实验结束前原始任务均已完成，不遗留清理任务，
也不删除真实锁或启动竞争的删除操作。

## 解释与限制

这些行为属于既有设计，已由 `packages/shared/tests/file-lock.test.ts` 和
[生命周期说明](../architecture/2026-10-10-effect-file-lock-lifecycle.md) 覆盖。
本探针使其无需完整应用即可独立运行，不修改锁策略，也不建议超时终止持有者。

这修正了此前过宽的诊断：两分钟获取超时不等于整个启动过程限时两分钟。
清理超时可产生该错误类别，但阻塞合成删除不能复现 CPU 饥饿，也不能证明线上
错误由此造成。实验没有展示循环等待。独立的历史工作量探针检查不同机制；
两者都不能验证新 SDK 上的旧在线状态队列假设。

本分支不包含真实日志、对话或凭据。进一步归因需要完整嵌套错误和关联跟踪，
修改全局超时不属于本诊断范围。
